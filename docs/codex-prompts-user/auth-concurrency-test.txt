동일 refresh token 으로 동시에 2회 이상 재발급 요청 시
오직 1건만 성공하고 나머지는 무효 refresh 로 실패하는지 검증한다.

[작업 전 필수]
1. refresh 로직 구현부를 먼저 읽고 요약해라.
2. UserSessionRepository 에 잠금 조회 또는 version 처리 방식이 어떻게 들어갔는지 먼저 확인해라.
3. 기존 테스트 스타일에서 동시성 테스트를 어떻게 작성할 수 있을지 먼저 판단해라.
4. 실제 DB 락 검증이 어려우면 서비스 레벨에서 재현 가능한 최소 테스트 전략을 먼저 설명해라.

[이번 브랜치 목표]
refresh token rotation 과정의 동시성 문제를 검증하는 테스트를 추가하고, 필요 시 최소한의 보완을 한다.

[검증해야 할 시나리오]
- 동일한 refresh token으로 동시에 2개의 refresh 요청
- 한 요청만 성공
- 나머지 요청은 currentJti 불일치 또는 rotation 이후 토큰 불일치로 실패
- 로그아웃 후 refresh 실패
- 탈퇴 후 refresh 실패

[구현 원칙]
- 테스트를 위해 운영 코드를 과도하게 훼손하지 마라.
- 동시성 검증이 어려우면 왜 그런지 설명하고 가능한 범위에서 가장 신뢰도 높은 테스트를 작성해라.
- PESSIMISTIC_WRITE 또는 현재 선택한 방식이 실제로 어떤 효과를 가지는지 설명해라.

1. 참고한 기존 파일 / 패키지 요약
2. 생성 / 수정한 파일 목록
3. 파일별 핵심 변경 요약
   - 어떤 파일을 왜 바꿨는지 1~3줄씩 간략하게
4. 동시성 테스트 전략 설명
5. 실제로 보장되는 것과 한계 간단하게 설명
6. 최종 남은 TODO
