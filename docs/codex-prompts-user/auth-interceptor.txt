현재 작업 브랜치는 feat/36-auth-interceptor 이다.
이 작업은 feat/36-auth-refresh-logout 이 반영된 상태를 기준으로 한다.

기존 bread / breadrecord / user / auth 구현, AGENTS.md, docs/user-part-spec.md를 먼저 읽고 같은 스타일로 최소 수정 방식으로 이어서 작업해라.

[작업 전 필수]
1. 현재 AuthController, AuthService, JwtTokenProvider, UserSession 구조를 먼저 읽고 요약해라.
2. global.config / global.interceptor / global.filter 패키지 구조를 먼저 확인해라.
3. 기존 API 중 인증이 없어도 되는 엔드포인트와 보호해야 하는 엔드포인트를 먼저 구분해라.
4. 현재 /users/me 와 bread 관련 API 중 인증 의존이 있는 것들을 먼저 정리해라.

[이번 브랜치 목표]
Spring Security 없이 Bearer Access Token 인증 인터셉터를 구현한다.

[인증 정책]
- 일반 API 요청은 Access Token으로 인증한다.
- Access Token은 1일 만료다.
- Refresh Token은 /auth/refresh 에서만 사용한다.
- refresh token으로 일반 API 인증을 허용하지 않는다.

[이번 브랜치에서 구현할 범위]
- AuthInterceptor 또는 Filter 구현
- Authorization: Bearer <token> 파싱
- access token 검증
- token type 검증(access만 허용)
- request attribute에 현재 사용자 정보 저장
  - userId
  - sessionId 정도를 우선 고려
- 인증 제외 경로 whitelist 설정
  - /auth/toss
  - /auth/refresh
  - /bread-types
  - 인증 없이 허용할 공개 조회 API가 있으면 현재 프로젝트 기준으로 자연스럽게 반영
- WebMvcConfigurer 또는 기존 config에 interceptor 등록

[구현 원칙]
- Spring Security를 추가하지 마라.
- 현재 프로젝트의 global 패키지 구조를 존중해라.
- 기존 bread / breadrecord API가 너무 크게 깨지지 않도록 최소 수정으로 연결해라.
- 예외 응답은 프로젝트 기존 흐름을 최대한 따른다.

[출력 형식]
1. 참고한 기존 파일 / 패키지 요약
2. 생성 / 수정한 파일 목록
3. 파일별 핵심 변경 요약
   - 어떤 파일을 왜 바꿨는지 1~3줄씩 간략하게
4. 어떤 엔드포인트를 인증 제외했는지 설명
5. request attribute 설계 설명
6. 다음 브랜치(/users/me controller)에서 참고할 포인트

작업 종료 전에 반드시 아래를 출력해라.
1. 이번 브랜치에서 생성한 파일
2. 이번 브랜치에서 수정한 파일
3. 각 파일별 핵심 변경점 한 줄 요약
4. 다음 브랜치 작업자가 먼저 읽어야 할 파일 목록
5. 다음 브랜치에서 이어서 해야 할 핵심 TODO
