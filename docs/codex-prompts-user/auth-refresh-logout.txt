현재 작업 브랜치는 feat/<issue-number>-auth-refresh-logout 이다.
이 작업은 feat/<issue-number>-auth-login 이 반영된 상태를 기준으로 한다.

기존 bread / breadrecord / user / auth 구현, AGENTS.md, docs/user-part-spec.md를 먼저 읽고 같은 스타일로 최소 수정 방식으로 이어서 작업해라.

User 엔티티에 tossUserKey 저장을 반드시 포함한다.
향후 unlink/withdrawal webhook 처리 시 tossUserKey 로 사용자를 찾는다.

[작업 전 필수]
1. AuthService, UserSession, JwtTokenProvider 구조를 먼저 읽고 요약해라.
2. repository 에서 lock 또는 version 처리가 가능한 패턴이 있는지 먼저 확인해라.
3. ApiResponse, 예외 처리, 한국어 메시지 톤을 먼저 확인해라.
4. 현재 refresh token 저장 방식(hash, jti, expiresAt)을 먼저 확인해라.

[이번 브랜치 목표]
Sliding Session 기반 refresh / logout 기능을 구현한다.

[인증 정책]
- Spring Security는 사용하지 않는다.
- Access Token 만료 시간은 1일이다.
- Refresh Token 만료 시간은 30일이다.
- refresh 요청이 성공하면 Access / Refresh Token을 모두 재발급한다.
- refresh 시 세션 만료 시간을 다시 30일로 민다.
- refresh token rotation을 적용한다.

[이번 브랜치에서 구현할 범위]
- POST /auth/refresh 구현
- POST /auth/logout 구현
- RefreshToken 검증 로직 구현
- currentJti 검증 로직 구현
- 새 refresh token 발급 및 hash 교체
- refreshExpiresAt 갱신
- logout 시 현재 session revoke 처리
- 필요 시 repository에 잠금 조회 메서드 추가
  - PESSIMISTIC_WRITE 우선 검토

[동시성 관련 요구사항]
- 같은 refresh token으로 동시에 여러 요청이 들어올 수 있다.
- session row를 잠그거나 그에 준하는 방식으로 한 번만 성공하게 만들어라.
- 먼저 처리된 refresh 이후 늦게 들어온 요청은 currentJti 불일치 등으로 실패시켜라.
- refresh token 재사용을 단순 만료가 아니라 rotation 이후의 잘못된 토큰으로 구분 가능하게 해라.

[구현 원칙]
- refresh token 원문은 저장하지 말고 hash 검증으로 처리해라.
- 예외 구조를 새로 과하게 만들지 말고 기존 흐름을 존중해라.
- 응답은 ApiResponse 구조를 유지해라.
- 이번 브랜치에서는 아직 인증 인터셉터로 일반 API를 보호하는 작업까지는 하지 마라.

[출력 형식]
1. 참고한 기존 파일 / 패키지 요약
2. 생성 / 수정한 파일 목록
3. 파일별 핵심 변경 요약
   - 어떤 파일을 왜 바꿨는지 1~3줄씩 간략하게 설명
4. refresh rotation / sliding session / logout 처리 방식 설명
5. 동시성 문제를 어떻게 막았는지 설명
6. 다음 브랜치(interceptor)에서 참고할 포인트

중요:
- 각 파일의 전체 코드는 출력하지 마라.
- 전체 파일 내용 대신 핵심 변경점과 필요한 코드 조각만 최소한으로 보여줘라.
- 내가 요청할 때만 특정 파일의 전체 코드를 출력해라.

작업 종료 전에 반드시 아래를 출력해라.
1. 이번 브랜치에서 생성한 파일
2. 이번 브랜치에서 수정한 파일
3. 각 파일별 핵심 변경점 한 줄 요약
4. 다음 브랜치 작업자가 먼저 읽어야 할 파일 목록
5. 다음 브랜치에서 이어서 해야 할 핵심 TODO
