현재 작업 브랜치는 feat/<issue-number>-auth-session-domain 이다.
이 작업은 feat/<issue-number>-user-domain 이 반영된 상태를 기준으로 한다.

기존 bread / breadrecord / user 구현, AGENTS.md, docs/user-part-spec.md를 먼저 읽고 같은 스타일로 최소 수정 방식으로 이어서 작업해라.

[작업 전 필수]
1. 현재 저장소에서 entity / repository / dto / service 패턴을 먼저 읽고 요약해라.
2. AuditingEntityListener, @CreatedDate, @LastModifiedDate, @Builder 스타일을 먼저 확인해라.
3. ApiResponse 사용 방식과 응답 DTO 네이밍 규칙을 먼저 확인해라.
4. 기존 코드에서 인증 관련 임시 처리(X-USER-ID 등)가 어디까지 들어가 있는지 먼저 확인해라.

[이번 브랜치 목표]
Sliding Session 기반 인증을 위한 auth 세션 도메인 뼈대를 추가한다.
이번 브랜치에서는 controller / API / SecurityConfig를 만들지 않고, 이후 login / refresh 브랜치가 바로 이어서 붙일 수 있는 세션 엔티티, 저장소, 필요한 service 수준까지만 만든다.

[인증 정책]
- Spring Security는 사용하지 않는다.
- Access Token 만료 시간은 1일이다.
- Refresh Token 만료 시간은 30일이다.
- Sliding Session 방식으로 간다.
- Refresh 시 Access / Refresh Token을 둘 다 재발급한다.
- Refresh Token Rotation을 적용한다.
- Refresh 성공 시 이전 Refresh Token은 즉시 무효화한다.
- 동일 Refresh Token으로 동시에 요청이 들어오면 1건만 성공할 수 있어야 한다.
- 이후 동시성 문제를 처리할 수 있도록 세션 구조를 준비한다.

[이번 브랜치에서 구현할 범위]
- domain.auth 패키지 추가
- UserSession 엔티티 정의
- UserSessionRepository 정의
- UserSessionService 수준의 최소 서비스 추가
- 세션 저장에 필요한 최소 필드 정의
  - id(sessionId)
  - userId
  - refreshTokenHash
  - currentJti
  - refreshExpiresAt
  - revokedAt
  - createdAt
  - updatedAt
- 이후 refresh 동시성 처리를 위해 repository에 잠금 조회 메서드 또는 그에 준하는 최소 준비를 한다.
- 단, 실제 login / refresh / logout 로직 구현은 다음 브랜치 이후로 넘긴다.

[구현 원칙]
- refresh token 원문은 저장하지 말고 hash 저장을 기본으로 고려해라.
- 현재 프로젝트에 BaseEntity가 없으면 억지로 만들지 마라.
- auth 관련 구조는 과하게 확장하지 말고 MVP 범위에 맞는 최소 구조로 둬라.
- 아직 controller / API / SecurityConfig는 만들지 마라.
- service는 세션 저장, 조회, 회전 준비 수준의 최소 로직만 둬라.
- 한국어 메시지 / Swagger 톤은 기존 스타일을 유지해라.

[출력 형식]
1. 참고한 기존 파일 / 패키지 요약
2. 생성 / 수정한 파일 목록
3. 파일별 핵심 변경 요약
   - 어떤 파일을 왜 바꿨는지 1~3줄씩 간략하게
4. 세션 구조를 이렇게 잡은 이유
5. 다음 브랜치(login 구현)에서 참고할 포인트

작업 종료 전에 반드시 아래를 출력해라.
1. 이번 브랜치에서 생성한 파일
2. 이번 브랜치에서 수정한 파일
3. 각 파일별 핵심 변경점 한 줄 요약
4. 다음 브랜치 작업자가 먼저 읽어야 할 파일 목록
5. 다음 브랜치에서 이어서 해야 할 핵심 TODO
