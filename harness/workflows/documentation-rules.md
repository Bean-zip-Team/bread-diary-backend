# Documentation Rules

## 기본 원칙

- 구현 판단의 기본 기준은 `docs/`가 아니라 현재 코드와 테스트다.
- `docs/`는 사용자가 명시적으로 요청했거나 문서 작업 자체일 때 우선 참고한다.
- 문서와 코드가 충돌하면 코드를 먼저 확인하고 문서를 갱신 후보로 본다.
- 코드를 확인할 때는 도메인 전체를 전부 읽지 말고, 현재 변경 범위를 이해하는 데 필요한 **최소 관련 파일**부터 본다.

## 코드 확인 방식

- 먼저 현재 작업과 직접 연결된 controller / service / mapper / repository / test만 확인한다.
- 기존 패턴 확인이 필요할 때만 같은 도메인의 인접 파일을 추가로 본다.
- 작은 수정이라면 관련 파일 몇 개만 보고 바로 구현으로 들어가는 것을 기본으로 한다.
- “코드를 먼저 본다”는 뜻은 전체 코드를 다 읽는다는 의미가 아니다.

## 우선순위

1. 현재 소스 코드
2. 현재 테스트
3. `AGENTS.md`
4. `harness/` 문서
5. `docs/`

## harness 문서 운영

- `harness/`는 프로젝트의 세부 작업 규칙 저장소다.
- 공통 규칙은 architecture/workflows 문서에 두고, 도메인별 규칙은 domains 문서에 둔다.
- 중요한 결정은 가능한 한 도메인 문서나 공통 규칙 문서로 분리해서 적는다.
